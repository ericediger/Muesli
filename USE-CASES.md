# What the Granola API enables that the app does not

Grounded in the current API (v1.5.0, September 2026) and the Granola help center. Items marked **built** are available today in this tool; **next** are natural extensions on the same foundation.

## What the API exposes

| Endpoint | Data |
|---|---|
| `GET /v1/notes` | Cursor-paginated list; filters `created_after`, `created_before`, `updated_after`, `folder_id`. |
| `GET /v1/notes/{id}?include=transcript` | Title, owner, attendees, calendar event, folder membership (including ancestors), AI summary (text + Markdown), **your private notes** (owner only), transcript. |
| `GET /v1/notes/{id}/transcript` | Paginated transcript for long meetings. Each item: `speaker.source` (microphone/speaker), `speaker.attribution` (`me`/`them`), `speaker.name` when speaker tags identified the person, `start_time`, `end_time`. |
| `GET /v1/folders` | Folder tree with `parent_folder_id`. |
| `GET /v1/audit` | Audit events (present in the OpenAPI spec). |
| `/v1/webhook-endpoints` | Subscribe to `note.generated`, `note.edited`, `note.access_granted`; Standard-Webhooks signatures; folder filters. |

Constraints worth knowing: only notes with an AI summary are returned; rate limit 5 rps sustained; personal keys see your notes + what is shared with you; workspace keys (admin) see public spaces only.

## Gaps in the app that the API closes

### 1. Selective, instant, structured export — **built** (`export`)
The app's only export is a CSV of your entire account, generated by email within "a few hours", once per 24 hours, link valid for 24 hours. The API lets you export any subset (by person, date, folder, keyword, or explicit IDs), immediately, as Markdown/text/JSON, with speaker labels and timestamps preserved.

### 2. Queries scoped to an explicit transcript set, with your own model and prompts — **built** (`ask`)
Granola Chat scopes to a meeting, a folder, People/Companies, or tick-boxed meetings, with Granola's models and prompt. Via the API you choose the exact notes, the model (Claude Opus 5 by default; any provider you hold keys for is a small extension), the system prompt, the effort level, and you keep the corpus cached for a whole session of follow-ups. Conversations are saved as files you can grep or feed elsewhere.

### 3. Person profiles for people the app does not know — **built** (`profile`)
The app's People view only populates from calendar-linked meetings; notes you start manually (nearly all of yours) leave it empty. The API plus your `YYMMDD - Name` title convention, attendee lists and speaker tags rebuilds the person→meetings relationship, and the profile pipeline turns all one-on-ones with a person into an evidence-backed EQ / IQ / professional profile. Nothing in the app aggregates a person's own words across meetings this way.

### 4. A durable, private archive — **built** (`sync`)
The `transcript-auto-deletion` help page and the `per_user_transcript_auto_deletion` / `transcription_retention_time_ms` flags show transcripts can be retention-limited by workspace policy; summaries can also be edited or regenerated. A scheduled `sync` keeps an immutable local copy including private notes. Combine with `note.edited` webhooks to record every summary revision.

### 5. Talk-time and interaction analytics — **next** (data already in `index.json`)
Every transcript item carries `me`/`them` attribution and timestamps, so you can compute per-meeting and per-person talk share, meeting length, speaking cadence, question rate, interruptions (overlapping `start_time`s), and how these trend over months. The index already stores `me_word_share`, `word_count` and `duration_minutes` per note; a `stats` command is a small addition.

### 6. Commitment tracking across meetings — **next**
The profile extractor already pulls `commitments_by_person` and `commitments_to_person` with quotes. Running it over all meetings (not only one person) yields a ledger of promises made, by whom, when, and whether a later transcript mentions them as done. The app's action items are per-meeting and not reconciled over time.

### 7. Event-driven automation — **next** (`webhooks` command exists)
Register an HTTPS endpoint for `note.generated`; on each new note, fetch it via the API and run any recipe: post a digest to Slack or email, file action items into Jira/Linear, write the note into an Obsidian/Notion vault with backlinks per person and company, or run the profile extractor incrementally. The app's Zapier/Slack integrations push summaries only, without your custom LLM step.

### 8. Cross-meeting topic timelines — **next**
Because you control the corpus, you can ask longitudinal questions the app struggles with ("how has our pricing position shifted since June, with dated quotes") and, with the JSON export, build topic timelines or a knowledge graph in your existing memory/graph tooling.

### 9. Self-coaching from your own words — **next**
`me`-attributed lines across hundreds of meetings are a corpus of how you communicate. Run the same profile pipeline on yourself, or ask for patterns: how you open meetings, how often you interrupt, how you handle pushback, filler-word rate.

### 10. Multi-model comparison — **next**
You hold keys for several providers. Because the corpus is a plain text block with an XML wrapper, the same question can be sent to two or three models and the answers diffed. The LLM layer is isolated in `src/llm/anthropic.ts`; adding a second provider is one file.

### 11. Private notes in context — **built** (included in `export` by default; Ask and Profiles use transcripts only)
Since v1.5.0 the API returns the notes you typed yourself during the meeting. Export includes them by default. On the CLI, `ask --content both` adds them to the corpus so the model can reconcile what you wrote with what was said, and `--no-private` then excludes them.

### 12. Audit and access transparency — **next**
`GET /v1/audit` exposes access events; a periodic pull lets you see what has been read via API keys and MCP in your workspace.

## What the API does not do (so you know where the edges are)
- No write access to notes, summaries or folders; no creating or editing notes.
- No people/company directory endpoint; person resolution is done client-side from titles, attendees and speaker tags.
- No full-text search endpoint; search is local over the synced archive.
- No audio; transcripts only.
- Notes without a generated summary are invisible to the API.
